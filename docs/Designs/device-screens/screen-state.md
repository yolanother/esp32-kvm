# Device screen state

The firmware display model derives a 240×240 view from copied, confirmed router and pairing status. Rendering cannot change the active route. The board LCD remains disabled at startup until its pins, orientation, backlight, and recovery behavior are validated on hardware. PLUS and touch inputs also remain disabled pending pin mapping; BOOT runtime hold still requests an emergency release.

The view priority is recovery, update, paused, pairing, guest list, then active target. Recovery and update take precedence over stale routing. A disconnected USB link or routing fault shows **INPUT PAUSED**. The active target names a guest only when the status says it is armed; otherwise it shows **DISARMED** or **HOST**. Guest rows use reported capacity and ready bits, and offline rows are never touch-selectable. Touch hit testing returns a request slot only; host arbitration must still acknowledge selection. The screen never treats a request as an active target.

A numeric comparison appears only when pairing state is challenge, the challenge ID is nonzero, the six-digit value is valid, and its monotonic deadline is in the future. The display derives the remaining seconds locally and removes the number when the deadline passes. It never logs or persists the number. Rejected, full, and expired pairing states show distinct retry guidance. Update progress is capped visually at 100 percent; recovery guidance supersedes update progress.

`kvm_transport_display_status` projects serialized USB worker facts into the screen status. It uses the confirmed open USB/router session, selected route and generation, queued pairing event state, and the bounded lookup of the authenticated current peer's opaque token. The display reports one guest slot only while that current peer token exists; it marks that slot ready only with the bounded HID readiness result. It does not turn the retained inventory of up to eight bonds into selectable live slots. If an armed route loses readiness, the screen shows a routing fault and does not name an active guest. Disconnect or an unopened session clears displayed pairing and route state. A challenge is shown only before its deadline with a valid ID and six-digit value; its number is cleared from projected status on expiry or failure.

There is no firmware update progress, recovery state, touch driver, or intentional guest-list request producer in this build. Their fields remain false and the LCD panel remains disabled at startup until its pins and orientation are physically validated. These views are therefore model behavior, not claimed live hardware behavior.

Portable verification: `firmware/tests/integration/run-msvc.ps1` covers producer-to-render pairing and live guest mapping; `firmware/tests/display/run-msvc.ps1` covers priority rules, disarmed target, rows, touch eligibility, challenge deadline, and button sampler. Native verification uses ESP-IDF 5.5.1 `idf.py -C firmware build` from the isolated worktree. Neither command accesses the device port.
