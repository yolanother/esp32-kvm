# Device screen state

The firmware display model derives a 240×240 view from copied, confirmed router and pairing status. Rendering cannot change the active route. The board LCD is disabled by default. The explicit `CONFIG_KVM_DISPLAY_WAVESHARE_TOUCH_154_VERIFIED` board profile enables its ST7789/SPI/LVGL startup after physical verification. `CONFIG_KVM_DISPLAY_CST816_TOUCH_VERIFIED` separately enables CST816 touch only after pin, orientation, and hit-region validation. PLUS remains disabled. BOOT runtime hold requests emergency release even if panel startup fails.

The view priority is recovery, update, routing fault or armed-without-ready-guest (paused), pairing, guest list, then active target. Recovery and update take precedence over stale routing. A disconnected USB link (no PC app session) no longer pauses the screen: see the table below. A routing fault always shows **INPUT PAUSED**. The active target names a guest only when the status says it is armed; otherwise it shows **DISARMED** or **HOST**. Guest rows use reported capacity and ready bits, and offline rows are never touch-selectable. Touch hit testing returns a request slot only; host arbitration must still acknowledge selection. The screen never treats a request as an active target.

### No PC app session (USB off)

With no host session the board shows the same active screen as with a session. Only two things differ: the This PC card (the USB-attached host) is dimmed to 50% opacity while the guest cards stay at full opacity (geometry and touch targets unchanged; opacity is reapplied on every redraw, so it restores when the session returns) and the footer shows a badge instead of "Selected target is highlighted". The badge lists the USB state first, then each connected device-owned input:

| USB | Keyboard | Mouse | Footer badge |
| --- | --- | --- | --- |
| off | no | no | `USB off` |
| off | yes | no | `USB off \| KB` |
| off | no | yes | `USB off \| MS` |
| off | yes | yes | `USB off \| KB MS` |
| on | no | no | `USB on` |
| on | yes | no | `USB on \| KB` |
| on | no | yes | `USB on \| MS` |
| on | yes | yes | `USB on \| KB MS` |

The badge is shown only while dimmed (no session); with a session the normal footer is used. It is redrawn only when its text changes. The screen no longer pauses for a missing USB session. Only a routing fault, recovery, a firmware update, or an armed route without a ready guest pauses input; pairing and guest-list screens keep their precedence and are never dimmed.

### Input devices (keyboard and mouse owned by the board)

The keyboard button left of the guest settings gear (same gate: touch, at least one paired guest, no fault, no armed host route, no open guest pairing window) opens **INPUT DEVICES**, a list of three touch rows: `KEYBOARD: <name>` or `KEYBOARD: not paired`, `MOUSE: <name>` or `MOUSE: not paired`, and `ADD KEYBOARD OR MOUSE`, which opens the 30-second pairing window (scan rows, passkey, result) as before. The close control leaves the list; the list closes on its own after 30 seconds without a touch.

Tapping a paired row asks for confirmation: the title becomes `FORGET <name>?`, the row reads `TAP AGAIN TO FORGET` and the footer `Tap again within 5s`. A second tap on the same row within 5 seconds forgets that device (the footer then shows `KEYBOARD FORGOTTEN` or `MOUSE FORGOTTEN`; a refused request shows `FORGET FAILED, RETRY` and keeps the row). A tap after 5 seconds, or on the other row, only asks again. Forgetting removes the record and the device's bond (never a guest's), drops a live link (held keys are released on the target first) and stops its reconnect attempts.

The USB worker owns this list, like the pairing window: the display only renders the worker's snapshot (`input_dev_*` fields) and queues touch requests, and only the worker calls the central (`doubtech_hid_central_forget`, and `doubtech_hid_central_stored` for the names). The list is never available while the host has a guest armed or a guest pairing window is open: opening or forgetting then shows **BUSY** with the cause, the host arming while it is open replaces it with **BUSY**, and a guest pairing request is refused while it is shown.

Stored devices reconnect on their own after boot and after they drop (10-second attempts, 15 seconds apart, one at a time, none during a pairing window). The `KB` and `MS` badge entries follow the connection immediately in both directions.

A numeric comparison appears in a 28-pixel font only when pairing state is challenge, the challenge ID is nonzero, the six-digit value is valid, and its monotonic deadline is in the future. The display derives the remaining seconds locally for both the waiting window and challenge, and removes the number when the deadline passes. It never logs or persists the number. Rejected, full, and expired pairing states show distinct retry guidance. Update progress is capped visually at 100 percent; recovery guidance supersedes update progress.

`kvm_transport_display_status` projects serialized USB worker facts into the screen status. It uses the confirmed open USB/router session, selected route and generation, queued pairing event state, and three authenticated live HID slots. The display counts ready guests and stores a separate ready mask for slot rows; it does not turn the retained inventory of up to eight bonds into selectable live slots. If an armed route loses readiness, the screen shows a routing fault and does not name an active guest. USB loss or an unopened session clears displayed route state but preserves the sampled BLE guest count. The USB worker separately owns on-device pairing state, so a guest-initiated numeric challenge remains visible without a host session. A challenge appears only before its deadline with a valid ID and six-digit value; its number clears on bonding, rejection, or expiry, rather than when the board automatically accepts its side.

There is no firmware update progress, recovery state, or intentional guest-list request producer in this build. Their fields remain false. The CST816 driver is compiled but disabled by default. When validated and enabled, its interrupt wakes the display worker, which reads one touch point and maps the visible action row to Start or Cancel for manual pairing. A numeric challenge has no board approval button: the board accepts its side automatically, shows the code, and waits for confirmation on the guest. The callback queues a fixed-size request; the USB worker checks ownership and deadline before making a bounded NimBLE host request. Invalid, stale, or overflowed requests have no effect. The six-digit number is never logged or persisted. BOOT emergency release clears the touch queue and cancels pairing. The LCD turns its backlight off before SPI initialization and on only after the first derived status view has been rendered.

## Validated board profile and physical gate

The intended board is Waveshare **ESP32-S3-Touch-LCD-1.54**, with a 240×240 ST7789 panel and CST816 touch controller. The panel profile assumes SPI clock GPIO38, MOSI GPIO39, CS GPIO21, DC GPIO45, reset GPIO40, and active-high backlight GPIO46. The driver uses 40 MHz, RGB565, inversion on, and SPI mode 0 as described by Waveshare. The touch profile assumes I2C SDA GPIO42, SCL GPIO41, reset GPIO47, and interrupt GPIO48 from the [Waveshare schematic](https://files.waveshare.com/wiki/ESP32-S3-Touch-LCD-1.54/ESP32-S3-LCD-1.54-Schematic.pdf). Touch orientation and hit regions require independent physical validation. PLUS remains unassigned.

1. Record the printed board model/revision and compare the LCD/backlight pin mapping with the [Waveshare product page](https://docs.waveshare.com/ESP32-S3-Touch-LCD-1.54) and [schematic](https://files.waveshare.com/wiki/ESP32-S3-Touch-LCD-1.54/ESP32-S3-LCD-1.54-Schematic.pdf). Check the BOOT-held USB recovery procedure before any panel-enabled flash. Keep the first test USB powered, with no battery.
2. Build and retain the default `n` profile as the recovery baseline. For the controlled panel test, set `CONFIG_KVM_DISPLAY_WAVESHARE_TOUCH_154_VERIFIED=y` in local ESP-IDF configuration, reconfigure, and build. Do not check the generated `sdkconfig` into source control. The tracked `sdkconfig.defaults` enables the 28-pixel comparison font but does not enable the panel.
3. The hardware owner flashes the controlled build, then confirms normal boot/USB handshake and that BOOT still triggers emergency local release. Confirm the backlight comes on after the first status render, text is upright and readable, colors are correct, and there is no reset loop. If the screen stays dark or colors/rotation are wrong, restore the default profile before revising pin, mode, or orientation values.
4. Exercise a host-started pairing window and verified numeric challenge against a real guest. Check countdown, exact six digits on screen and host, expiry clearing, rejected/capacity guidance, and that no number appears in logs. Check USB disconnect, unready guest, armed guest, and local/disarmed target display against confirmed router state. Record board revision, photos, build digest, observed colors/orientation, and recovery result in the hardware task before considering the profile validated.

For interactive touch bring-up, retain the working panel-only image. Enable `CONFIG_KVM_DISPLAY_CST816_TOUCH_VERIFIED=y` only after checking the PCB revision and four touch pins above. The [Espressif CST816S driver](https://components.espressif.com/components/espressif/esp_lcd_touch_cst816s) may require `CONFIG_ESP_LCD_TOUCH_CST816S_DISABLE_READ_ID=y` because some controllers do not answer an idle ID read. First verify that left, right, top, and bottom touches land in their intended regions without opening pairing; then tap **START PAIRING** while USB is disconnected and verify the 60-second countdown. Also initiate pairing directly from a guest without touching the board: compare the six digits on both screens and confirm only on the guest. Check bonding, rejection, expiry, and a BOOT emergency hold. A stale or duplicate touch must not change pairing. Record physical observations, normal USB enumeration, and BOOT recovery before leaving touch enabled.

Portable verification: `firmware/tests/integration/run-msvc.ps1` covers producer-to-render pairing and live guest mapping; `firmware/tests/display/run-msvc.ps1` covers priority rules, disarmed target, rows, touch eligibility, waiting/challenge deadlines, and button sampler. Native verification uses ESP-IDF 5.5.1 `idf.py -C firmware build` from the isolated worktree. Neither command accesses the device port.
