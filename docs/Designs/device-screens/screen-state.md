# Device screen state

The firmware display model derives a 240×240 view from copied, confirmed router and pairing status. Rendering cannot change the active route. The board LCD is disabled by default. The explicit `CONFIG_KVM_DISPLAY_WAVESHARE_TOUCH_154_VERIFIED` board profile enables its ST7789/SPI/LVGL startup after physical verification. PLUS and touch inputs remain disabled pending pin and behavior validation; BOOT runtime hold requests an emergency release even if panel startup fails.

The view priority is recovery, update, paused, pairing, guest list, then active target. Recovery and update take precedence over stale routing. A disconnected USB link or routing fault shows **INPUT PAUSED**. The active target names a guest only when the status says it is armed; otherwise it shows **DISARMED** or **HOST**. Guest rows use reported capacity and ready bits, and offline rows are never touch-selectable. Touch hit testing returns a request slot only; host arbitration must still acknowledge selection. The screen never treats a request as an active target.

A numeric comparison appears in a 28-pixel font only when pairing state is challenge, the challenge ID is nonzero, the six-digit value is valid, and its monotonic deadline is in the future. The display derives the remaining seconds locally for both the waiting window and challenge, and removes the number when the deadline passes. It never logs or persists the number. Rejected, full, and expired pairing states show distinct retry guidance. Update progress is capped visually at 100 percent; recovery guidance supersedes update progress.

`kvm_transport_display_status` projects serialized USB worker facts into the screen status. It uses the confirmed open USB/router session, selected route and generation, queued pairing event state, and the bounded lookup of the authenticated current peer's opaque token. The display reports one guest slot only while that current peer token exists; it marks that slot ready only with the bounded HID readiness result. It does not turn the retained inventory of up to eight bonds into selectable live slots. If an armed route loses readiness, the screen shows a routing fault and does not name an active guest. Disconnect or an unopened session clears displayed pairing and route state. A challenge is shown only before its deadline with a valid ID and six-digit value; its number is cleared from projected status on expiry or failure.

There is no firmware update progress, recovery state, touch driver, or intentional guest-list request producer in this build. Their fields remain false. The LCD turns its backlight off before SPI initialization and on only after the first derived status view has been rendered. By default the LCD still never initializes. Source tests and a compiled panel path do not prove the actual board display.

## Validated board profile and physical gate

The intended board is Waveshare **ESP32-S3-Touch-LCD-1.54**, with a 240×240 ST7789 panel and optional CST816 touch controller. The selected profile assumes SPI clock GPIO38, MOSI GPIO39, CS GPIO21, DC GPIO45, reset GPIO40, and active-high backlight GPIO46. The driver uses 40 MHz, RGB565, inversion on, and SPI mode 0 as described by Waveshare. The actual panel waveform and color/orientation behavior must still be checked on this PCB revision before leaving the opt-in enabled. Touch and PLUS are outside this activation.

1. Record the printed board model/revision and compare the LCD/backlight pin mapping with the [Waveshare product page](https://docs.waveshare.com/ESP32-S3-Touch-LCD-1.54) and [schematic](https://files.waveshare.com/wiki/ESP32-S3-Touch-LCD-1.54/ESP32-S3-LCD-1.54-Schematic.pdf). Check the BOOT-held USB recovery procedure before any panel-enabled flash. Keep the first test USB powered, with no battery.
2. Build and retain the default `n` profile as the recovery baseline. For the controlled panel test, set `CONFIG_KVM_DISPLAY_WAVESHARE_TOUCH_154_VERIFIED=y` in local ESP-IDF configuration, reconfigure, and build. Do not check the generated `sdkconfig` into source control. The tracked `sdkconfig.defaults` enables the 28-pixel comparison font but does not enable the panel.
3. The hardware owner flashes the controlled build, then confirms normal boot/USB handshake and that BOOT still triggers emergency local release. Confirm the backlight comes on after the first status render, text is upright and readable, colors are correct, and there is no reset loop. If the screen stays dark or colors/rotation are wrong, restore the default profile before revising pin, mode, or orientation values.
4. Exercise a host-started pairing window and verified numeric challenge against a real guest. Check countdown, exact six digits on screen and host, expiry clearing, rejected/capacity guidance, and that no number appears in logs. Check USB disconnect, unready guest, armed guest, and local/disarmed target display against confirmed router state. Record board revision, photos, build digest, observed colors/orientation, and recovery result in the hardware task before considering the profile validated.

Portable verification: `firmware/tests/integration/run-msvc.ps1` covers producer-to-render pairing and live guest mapping; `firmware/tests/display/run-msvc.ps1` covers priority rules, disarmed target, rows, touch eligibility, waiting/challenge deadlines, and button sampler. Native verification uses ESP-IDF 5.5.1 `idf.py -C firmware build` from the isolated worktree. Neither command accesses the device port.
